# 原生 A/C 轨迹诊断与 v43 改进结果

2026-10-31，物理 GPU1，固定六条 DEV 链的一次探索性对照。

**本轮达到目标：C v43 的 SLO 达标链数为 5/6，原生 JITServe A 为 4/6。** 相对增加 25%，达标率由 66.7% 提升至 83.3%。A 原本达标的链 1、2、3、5 全部保留，新增链 4。链 0 仍未达标。

这只是在已经查看过的六条 DEV 链上取得的结果，不能据此声称泛化优势或统计显著性。新增链 4 的余量为 **0.766 秒**，当前胜出尚不稳健。

## 原有轨迹说明了什么

上一轮 native A / HF C v42 都达标 4/6，但 A 在六条链上全部更快。v42 在共享 HF 后端上胜过共享 B，不能直接推导为胜过原生 JITServe。

- A 的链 0 在阶段 3 开始执行前等了约 112.6 秒，最后以 242.1 秒错过 120 秒目标。
- A 的链 4 在阶段 4、5 开始执行前分别等了约 40.1、39.3 秒，最终 160.7 秒，错过 120 秒目标。它是一个可以通过资源安排挽救的候选。
- C v42 的链 0、3、4 虽然很快发出过首 token，但随后出现约 213–216 秒的连续执行间隔。只看 TTFT 会漏掉这种暂停。
- 旧主负载中，A 平均执行 batch 为 2.754，C v42 为 1.851；执行器调用累计等待墙钟约 208.9 秒与 481.9 秒。每次调用的平均等待约 32.3 ms 与 50.0 ms。批处理收缩和后端差异都很明显，不能把全部差距归于调度优先级。

上述“执行器等待墙钟”包含 Python/执行器等待，并非 CUDA event 时间；同一 batch 中各请求的执行时间重叠，不能把它们相加作为 GPU 时间。

## v43 改了哪些部分

v43 是独立的新 C 原型，使用与 A 相同的原生 vLLM `GPUExecutorAsync`、paged KV、模型和编译二进制。它替换了 v42 的 HF 执行路径及尾部风险/lease 规划路径，核心改为当前阶段的链级 KV 准入。

1. 在原生图匹配拆分阶段预算之前，用客户端收到的 `slo[2] × num_stages − served_time` 保存整链绝对 deadline。调度依据整链目标，不依赖 A 的阶段预算。
2. 把同一条链当前阶段的 compound 成员作为一个准入单位，按整链 deadline 排序。资源充足时继续动态批处理。
3. 为当前阶段预留 KV：当前 prompt 加上 QRF 预测输出或“已生成长度 + 50”中的较大值，并以公开的 `max_tokens` 限制预测。预留总量受原生 GPU 块数及 watermark 限制。
4. 紧迫阶段需要空间时，通过原生换出 API 暂停较后链，每个调度 tick 至多主动换出三个请求。换出专用执行步结束后才允许换入，避免同时复用块。
5. 仍有未超时的 READY 链时，暂缓已经超时的链；随后把所有请求排空。超大的 compound 会串行推进成员，避免因整组放不下而永久等待。

调度器不读取测试轨迹的未来 prompt/输出，不使用 `target_output_length` 或 `real_output_len` 计算准入，也没有按链 ID 特判。停止器仍按两臂原有相同规则完成固定输出长度回放。A 的启动代码与 stage8 字节一致，原生 A 的调度语义没有修改。

代码入口为 `programs/native_chain.py`、`programs/deadline_reservation.py` 和 `programs/c_server.py`。冻结 v42 的 70 个文件、官方 1297 个源码文件及 5 个原生运行文件均通过原始哈希复核。

## 同负载结果

同一物理 GPU1、相同原始前六条链、相同计划到达与 deadline、相同 BF16 Qwen2.5-7B-Instruct、引擎 seed 0、客户端 seed 42、相同采样与输出长度限制。每臂 40 个主请求 + 7 个热身请求。实际到达误差均在原冻结容差内。

资源均为 GPU 512 块 / 8192 KV tokens、CPU 1170 块、block 16、单引擎、最大并发序列 32、每步 tokens 2048、模型长度 8192、1 GiB swap、eager/chunked 开启、prefix caching 关闭。v43 每个原生调度 tick 更新准入；这是允许改变的 C 机制行为，资源上限不变。

## 新增达标链是怎样救回的

这轮链 4 的阶段 4 用时从 A 的 **40.841 秒降至 1.035 秒**，首个 forward 前等待从 39.698 秒降至 0.055 秒。这是整链提前约 40.584 秒的主要来源。

阶段 5 仍是瓶颈：A 为 77.719 秒，C 为 79.374 秒。C 虽然马上开始执行，但中途仍出现约 30.711 秒的连续暂停。v43 没有消除所有长等待，因此链 4 最终仅提前 deadline 约 0.766 秒。后续若继续改进，应重点研究紧迫链末阶段的暂停代价及保留执行机会，而不是把一次 5/6 当作稳定胜出。

## 有效性和结果边界

- 新增 7 项 CPU 检查通过，包含真实 pinned vLLM 调度器/块管理器的 chunked prefill、decode、换出、恢复和释放；冻结 v42 的 79 项检查也通过。
- 新 C 的三链兼容性检查先通过：28/28 请求完成、最大 batch 7、compound 宽度 3、预测和图匹配完整、KV 全释放；随后才执行新的 A → C 六链对照。
- 六链两臂均 47/47 请求完成；同 ID 的输入 SHA、采样参数、收到的 SLO、真实输出 token 数、finish reason 和 stop reason 全部一致。多阶段屏障和客户端完成时间检查通过。
- 记录了 289 条链级准入快照；全部 10748 次实际执行器调用与最近准入记录对齐，没有出现准入集合外的执行。21 次为空 batch 的真实换出专用调用，最终换入换出各 2740 块。
- 两臂完整输出 token-ID 序列哈希只有 **19/47** 一致。原因尚未定位，不能直接归因为舍入。这里验证的是固定长度、后续 prompt 不消费生成文本的公开 trace 回放；不能据此声称逐 token 语义等价或真实 agent 质量相同。
- 最终 1372 个基础文件 + 14 个 stage 文件 SHA 均匹配；全部 KV 块归还；进程和端口清理通过。GPU1 为授权 UUID、0 MiB、无 compute 进程。未在 GPU0/GPU2 启动实验。
