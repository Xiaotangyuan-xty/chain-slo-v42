# v50: anytime, stage-aware token-credit window projection

The target is fixed-hour JITServe weighted-token goodput above 1000/s, with 1100/s as a stretch goal on the frozen Llama8B mixed workload. **These are experiment goals, not measured results or validity gates.** No v50 GPU result is claimed at release time.

v49pro's complete traces showed 5583/5538 joint plans and zero committed candidate sets. Most plans exhausted a 6ms budget while simulating the full continuation, and the fallback retained native A's uncorrected stage budgets. The original v49pro code/data and its supplemental acceptance evidence remain intact.

## Mechanism

Production entry: `stage43_v50_window_projection_20261108_v1/programs/install_comparison_runtime.py`, explicit method `v50`. It installs `MixedScheduler` from `mixed_joint.py`; that scheduler imports `window_control.plan`, not the old full event-rollout planner.

* `window_projection.py` prepares each donor stage envelope once per planning event. Future stages keep declared width, prefill, context, and barrier costs. Peer background phases use a common public-prediction timeline. Alternatives differ only in service during the same bounded window; continuation assumptions and donors are shared. This replaces repeated whole-cohort event simulation with cached array projections.
* Root value is conditional terminal weighted-token credit. A monotone weighted CDF interpolates between historical scenario completion times; below the shortest scenario the credit is zero, above the longest it reaches the full mean. Each next donor's credit weights its interpolation interval. This gives a marginal signal between sparse support points without changing the measured native goodput formula. **The piecewise-uniform assumption is not a calibrated probability guarantee.** Foreground incremental credit follows native cumulative token deadlines and excludes already earned prompt/decode credit.
* Native pack, incumbent, pair-add/remove/exchange, and bounded focus packets are evaluated. Focus keeps fresh latency prefills and can pause at most eight current members; every resident/reference loss remains in the objective. Unrelated constant credit does not inflate the switching margin. A completed positive improvement survives later search-budget exhaustion; incomplete comparisons never become zero-loss proposals.
* CPU swap space is reserved jointly in the actual eviction order. Overflow is priced as recomputation for exactly the affected members, including foreground prefix replay. The executor still enforces physical KV/slots, swap availability and at most three swaps per iteration. No request is dropped and no deadline is extended.
* `step_cost.py` pre-indexes context/prefill cells and their width envelopes. Queries use cached nearest cells plus width bisection, rather than scanning all strata repeatedly. Samples still measure executor **host wall time**, not pure GPU kernel latency.

`planner_config.py` is the immutable source for the comparison contract: 10ms soft planning budget, 2ms finalization reserve, at most 20 completed sets, 16 donor scenarios, six challenger actions, eight displaced running members, native 50-token service quantum, and a minimum marginal gain of eight weighted tokens plus a relative margin on changed credit. The full 12ms planning reserve is charged in projected deadlines. Budget checks are cooperative, not a portable hard real-time guarantee; unsafe overruns return to native execution.

The candidate's native reference now uses the same current-stage-inclusive DR/implicit-ToT budget repair as Astar, declared in `V50_BUDGET_ADAPTER.json`. That repair is a foundation, **not claimed as novel**. A keeps original stage budgets; Astar keeps its existing repair. All methods receive the same inputs, SLO, arrivals, resource caps, predictor weights, framed protocol, dynamic-snapshot repairs and executor observer.

The pure DR core and both frozen length banks remain byte-identical to the parent. Native ToT remains implicit `[3,1,3,1]`, cap256. Parent mathematical helpers/tests are retained for regression; the old `mixed_control.py` is not the production scheduler entry. Some inherited diagnostic counter/observer marker names contain `v49pro`; the actual installed mechanism is identified by `V50_RUNTIME.json.version` and the explicit method label.

## Review and qualification

`CODE_REVIEW_V50.md` records the pre-submission review, defects found and their checks. The release includes the **actual deployment harness**, not only policy code:

* Explicit experiment root is passed to the native metric oracle and bound in the protocol. No case-parent-depth inference remains. A full completed nested GPU0 data set is recomputed read-only with the correct root, yielding exactly 3,174,614 fixed-hour and 3,215,763 complete-replay weighted tokens. A wrong root fails early.
* Baseline server snapshots and warmup gates handle A/Astar having no candidate cost model. All three methods require real executor events; only v50 must match candidate cost samples. Actual native A/Astar/v50 implicit-ToT and keyword APIs are qualified in fresh CPU processes.
* Six-case matrix tests verify per-card `v50 → A → Astar`, unique identities/ports, exact Llama8B/10176-block binding and rejection of wrong order/device/resources. CPU-only deployment preview directories cannot be launched by start, runner or controller.
* Pure DR decisions, prefix-preserving swap/recompute, full protocol completion, KV release, observer metadata/constructor hooks, model-bound stop behavior, weighted-credit mathematics and anytime behavior are tested.

Final native CPU qualification and exact source hashes are in `evidence/v50/CPU_QUALIFICATION.json`; run `python3 verify_v50_freeze.py`. CUDA visibility is empty and CUDA initialization is asserted false. `DEPLOYMENT_DRY_RUN.json` binds an actual preparation of six cases and all method routing/model/stop/prediction checks; it launched **zero** GPU processes and made **zero** formal main calls.

The 64 deterministic, evenly spaced snapshots in `assets/TRACE_PUBLIC_SNAPSHOTS.json` reconstruct public state available at each old v49pro decision. Membership matches every recorded snapshot. They expose only current QRF predictions, observed prefixes/completions and already observed executor costs; future outputs/arrivals are not given to the planner. Their native ordering is a corrected-uniform-stage-budget proxy, so this is **open-loop timing/action-path qualification**, not an exact GPU counterfactual or a goodput prediction. The release evidence reports completed comparisons, actual proposed interventions and CPU wall time without calling them GPU gains. These are development fixtures; independent frozen evaluation arrays/seeds are still needed for generalization claims.

        port=prediction_port, predictor_protocol="length_framed_pickle_v1")
