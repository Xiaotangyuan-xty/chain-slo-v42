## 一、研究目标与判定边界

### 1. 原始研究问题

在共享真实 backend 上，比较完整官方 JITServe 与自有链级 SLO 机制，区分：

- **B**：完整官方 JITServe policy、QRF、GraphMatchContext、50-tick frame、动态 batch/sliding-window；不是 cap4 简化版。
- **C**：自有链级 SLO 机制，使用相同公开输入、deadline、生成配置、KV/token 资源和 backend。
- 早期 A/B 区分用于识别原生 JITServe 与共享 harness 的差异；当前主要证据是 B/C，因此不能把 C>B 直接解释为所有系统层面的普遍算法优势。

### 2. 最新用户目标

最新有效胜利条件是：

> **C 的官方缩放 SLO 达标链数必须严格大于 B。**

补充约束：

- JCT、原生 request goodput、严格整链指标、尾延迟和开销要完整报告，但**不再设 JCT/goodput 优劣阈值**。
- 所有请求必须最终完成；同 ID 输出 token 数和 stop reason 一致；源码 SHA 通过；KV 无账分歧；自身进程清理且 GPU0 释放。
- 单次六链结果只代表冻结 DEV 负载的小样本现象，不是统计显著性或普遍 superiority。
- 不得通过换链、调 deadline、加资源、删失败记录、追加 seed 或打开 HOLDOUT 来制造胜利。

### 3. 历史判据变化（避免误读旧收据）

- 早期要求：C 的 SLO 达标数不少于 B、原生 goodput 严格更高、平均 JCT 严格更低。
- 中期改为：SLO 达标数严格更多，且平均 JCT 在 B 的 90%–110% 内。
- 最终改为：**只看 SLO 达标链数严格更多**，JCT 只报告。
- 因此，旧收据中的 `mechanism_won` 字段必须结合当时的 `comparison_valid` 和判定规则阅读。15 号虽然 JCT/goodput 有局部优势，但资格无效，不能算胜利。

## 四、最终代码状态（v3_chain_dynamic_v39）

当前不是早期冻结 v2 的原样，而是经过多次修复后的版本。主要语义如下：

1. **动态 backend**：不再按 4 拆批，恢复官方动态 batch/sliding-window；B/C 都保留官方 QRF 与 graph matching。
2. **官方 collective**：恢复官方对并发成员剩余 decode 时间的求和；v38 的 max 关键路径改动已撤销。
3. **候选与风险**：初始救援使用 EDF；候选必须是 CAL 风险可达标链。`risk_q=3.856` 来自 295 个 FIT 图和 99 个独立 CAL 图的 graph-max 标准化残差中位数，不是 DeepResearch JCT 覆盖率保证。
4. **统一风险账**：续租和候选使用同一 `forecasts()`，包含 GPU/host KV、恢复和重 prefill 成本；incumbent 在第二次 view 重建时显式保留。
5. **lease**：当前禁止 lease switching/yield；可达标锚链续租但不每帧重新规划。非边界 tick 也维护真实优先级与执行账。
6. **fallback**：未接受模型动作时每个官方帧都重新评估，修复了 fallback 锚点永不释放导致长期无候选的问题。
7. **优先级**：可达标链使用官方 JITServe 原生优先级；只有不可达标链持续延后，待可达标链完成后恢复执行。远期但仍可达标的链不再被额外推迟。
8. **资源动作**：planner 支持真实 waiting/running/swapped/compound 成员、token chunk 和 KV 预算；不可达标 KV 可回收。可达标链只有在其 slack 覆盖风险工作、lease 和往返恢复成本时才允许换出，且不再按 deadline 先后禁止恢复。
9. **host 满处理**：vLLM 或真实 backend ledger 的 host 空间任一不足时，放弃本次自定义控制并返回合法空 scheduler outputs，回退官方路径；不执行重计算或强行 swap。
10. **清理与审计**：清理异常也写 server audit；controller 对异常 server exit code 报错，不再把 client success 当作整臂成功。

当前比较器最终规则为 `small-full-dynamic-bc-comparison/v3`：只要求 C 的官方缩放达标链数严格大于 B，其他指标仅报告。

## 七、结果趋势与机制诊断

### 1. 总体结论

- 27 份比较收据中 17 份资格有效；没有 C>B 的有效胜利。
- 资格有效的 3 对 3 出现在 11、23、24、25、27、28、29、30 号；它们只是持平，不满足最终“严格更多”。
- 早期 03/06/07 的动作执行、lease、输出失败使结果无效。
- 15–19 号主要失败是多目标可区分性和超容量候选，而非真实端到端机制收益。
- 25 号首次稳定证明**链 1 可以新增达标**，但链 5 失去达标；26 号恢复优先级又使链 2 失效，随后撤销。
- 33 号证明**链 5 也可以被救回**（237.69 秒，约 240 deadline 内），但链 1/2 失效，说明仍是在链间转移损失，而不是共同改善。
- 最终 39 号为 B 的 2/3/5 达标，C 的 1/3 达标；C 新增链 1，失去链 2 和链 5。

### 2. 主要机制瓶颈

1. **整链与 request-level 目标冲突**：官方优先级可以保护 2/3/5，却使链 1 的 compound 阶段和长末段超时；简单提升锚链又会伤害其他链。
2. **抢占与 KV 抖动**：20/22 号分别出现 27/29 次 preempt、3498/4527 组 swap-out；22 号 KV 搬运约 4.14 GB，远高于同期 B 的约 192 MB。长期续租与频繁切换都可能造成此类回退。
3. **资源可行性并不等于实际收益**：`slack >= risk_work + lease + recovery` 只能排除明显危险动作，不能保证换出后按时恢复，也不能预测真实干扰。
4. **预测支撑域有限**：旧 `away_mean=16.036` 来自合成负载 decode-time 单位，不是公开 DeepResearch 的真实工具等待标签；不能拿它做真实可行性真值。baseline rollout 也曾误判链 2 超时、链 4 达标，不能当硬标签。
5. **状态机曾掩盖真实问题**：fallback 锚点不扣减、非边界 lease 不执行、第二次 view 重建丢失 incumbent，都导致长期无候选或选择退化；这些必须先于算法调参检查。
6. **运行时正确性优先**：重计算曾造成输出截断，关键路径 max 曾触发 KV planning conservation 错误。任何 SLO 改进都必须先通过同 ID 输出和 KV 账，否则不是机制收益。

### 3. 给后续模型的优先分析顺序（不是自动执行许可）

1. 先读 25、29/30、33、39 的 `server_audit_summary.json`、`client_calls.json`、`executor_events.jsonl`，按阶段分解链 1、2、5 的等待、服务和 KV 变化，找出能否同时保住三者，而不是继续盲目换 heuristic。
2. 以 25 号的链 1 增益和 33 号的链 5 增益为两个独立事实，核对实际 resident-set、swap-in/out、frame 成员和恢复时间，寻找可共同成立的调度区间。
3. 优先修正真实 planner 的原子性、恢复可证性和 host/GPU 两本账一致性；不要用更大的 KV、更多 seed 或换链规避。
4. 保留 37 号的无重计算回退、39 号的输出/清理检查，不能为了链数重新引入 C36 的输出截断或 C38 的 KV conservation 失败。
5. 只有在形成可解释的新机制版本后，才重新跑 CPU 和同一冻结 B/C；若需正式矩阵或 HOLDOUT，必须先获得用户明确授权。

## 十、交接结论

本阶段已经证明了完整动态 B/C、真实大 batch、官方预测/graph、输出契约、资源账和失败审计可以运行，但还没有证明自有机制在 SLO 达标链数上优于完整 JITServe。链 1 和链 5 分别被救通过，但尚未同时保住。

**最终有效结果：B=3、C=2，未获胜；实验已按用户要求停止。** 后续模型应先做只读证据分析，等待用户通知后再决定是否恢复实验。
